Thesis

The platform path makes it repeatable

Temporal makes durable execution possible, but the platform path makes it repeatable.

OpenAI @ Replay 2026 — From Adoption to Production at Scale

Most Temporal training teaches you to write a workflow. This teaches you to build the platform underneath it. The north star is the talk’s own headline metric — time-to-first-workflow, from one-to-two weeks down to minutes — and the final challenge measures it with a stopwatch.

The architecture takes one deliberate position against its own source material. OpenAI replaced Terraform with a Kubernetes operator because Terraform was making them slow. We keep Terraform as the execution engine inside a single activity, and build the control loop as a Temporal entity workflow instead of a k8s controller — because a workflow is a strictly better operator: durable by construction, retryable, auditable, and able to wait on a human. That claim is a ten-minute discussion in challenge 5, not a lab.

Seven rules

What the design guarantees, and why

Guarantees single-writer per resource

Workflow ID is the resource identity, so Temporal is the lock

One entity workflow per logical namespace, keyed on its name and started with signal-with-start; one child per physical namespace. Temporal’s own workflow-ID uniqueness constraint gives single-writer-per-resource for free.

Therefore: no lock table, no lease, no terraform force-unlock, and the state service implements no LOCK/UNLOCK endpoints at all. Terraform’s http backend treats locking as optional — omit lock_address and it never locks. Leave a comment saying why: a student who notices and asks “isn’t that dangerous?” is one question from the best insight in the workshop.

Guarantees no secret in state or event history

Credentials never pass through Terraform

temporalcloud_apikey exposes .token as a readable attribute, and sensitive = true masks CLI output without encrypting state. Minting keys in Terraform would put every student’s live credential in plaintext on a Fly volume.

So keys are not a Terraform resource. A separate activity calls the Cloud Ops API, writes to Vault, and returns a Vault path and a key id — never the token. One rule, three problems solved: nothing sensitive in state, nothing sensitive in event history, and rotation stops being state surgery. It also draws the Terraform-versus-API boundary where a real platform team draws it, since terraform destroy would otherwise revoke every worker’s auth.

Guarantees least privilege that actually works

A Developer-role service account is exactly sufficient

Verified against the permissions reference: Developer can create namespaces and receives Namespace Admin on the ones it creates — which is precisely what is required to manage namespace-scoped service accounts, mint their keys, and set tags. The platform needs no account-admin power. This is also why metrics_endpoint fell out of scope: it needs an account-scoped identity the platform deliberately lacks.

Guarantees config cannot drift from code

Config is generated from the decorated workflow

The decorated workflow is the source of truth. gen-config imports the modules and emits worker config from the live registry. Python owns it because that is where the decorators are; nsctl worker gen-config is a façade that shells out — better UX, and a real lesson: a platform CLI is a user interface, not a place where logic lives.

Guarantees a missing registration is loud

The worker refuses to start on a config mismatch

On boot the managed worker compares its config against the workflows it actually registered, and exits non-zero naming the discrepancy. Not a warning — a warning in a pod’s logs is a warning nobody reads. This is the direct fix for the failure the talk names: “always register that workflow at bootstrap; often times people miss that.”

Guarantees drift is caught, not just intent

Intent arrives by signal; reality arrives by timer

Both transports, deliberately. A git post-commit hook signals the reconciler so students get instant feedback; a durable timer poll catches what nobody committed. The distinction is the lesson — signals carry intent, the timer catches drift.

Guarantees the contract sits where languages meet

The schema guards the worker config, not the spec

The namespace spec never leaves Go, so a schema file there is overhead. What crosses the seam is the worker config: emitted by Python, consumed by the Python worker on boot and by the Go CLI when it templates a manifest. schema.json and the golden round-trip fixture guard that file only.

The asymmetry between the first two rows is a teaching beat, not an embarrassment: “You hold Global Admin because this is a workshop and you need to see everything. Your platform holds Developer because that is what production looks like — and notice it was enough.”

Granting a user namespace access is a user-management operation requiring Global Admin, so the platform cannot do it. The alternative — an elevated account-admin credential inside the reconcile path — would reintroduce exactly the second credential the portal deliberately deleted from its providers.tf.

Students authenticate by SAML against an Okta tenant rather than an emailed invite link. The role assignments above are unchanged.

The arc

Five challenges

1

Spec to workflow

Write the spec schema. nsctl apply -f starts a workflow, one activity runs Terraform, one namespace appears. Imperative on purpose — a student’s first twenty minutes need a visible win, and a declarative loop that silently does nothing has four candidate failure points.

GradedNamespace exists with the right retention, via Ops API.

2

Fan-out and identity

Parent entity workflow, one child per environment. A namespace-scoped service account per environment; the API key minted outside Terraform and written to Vault, the activity returning only a path.

GradedTwo namespaces and two service accounts via Ops API; the Vault path resolves.

3

Invert to declarative

Same activities, new driver: commit the spec, the hook signals, the reconciler reconciles. Change retention in the Cloud UI behind its back and watch the timer catch the drift. Delete an environment and watch the cleanup.

GradedQuery the reconciler for a drift-corrected result.

4

The paved road

A decorated workflow declares its own queue and namespace; gen-config emits the worker config; nsctl templates the manifest; the worker lands on k3s. Vault auth switches from root token to Kubernetes auth as a graded step — the one moment where “the worker moved into the cluster” has a consequence the student must handle rather than observe.

GradedWorker pod healthy, polling the right queue in the right namespace.

5

Be the developer — stopwatch

New persona, empty directory, timed. From nothing to a completed workflow using only the platform you built. Then ten minutes on why OpenAI abandoned Terraform for an operator, and what a Temporal-based control loop gets right that a k8s controller cannot.

GradedA workflow completed in the provisioned namespace within N minutes of the challenge starting.

Grading strategy

Three layers. Cloud-side state via the Ops API, following the portal’s approach. Platform-side behaviour by Query on the student’s own reconciler workflow — drift detection is invisible to the Ops API but plainly readable from workflow state, and it costs one Query handler. And the stopwatch, which makes the thesis measurable.

Self-paced means nothing can be graded by walking the room. The portal’s sharp edge #7a admits its Grafana dashboard was unverifiable and the mitigation was “look at screens.” That option does not exist here, so every checkpoint must be machine-verifiable from the Ops API or from inside the sandbox.

Challenge 4 is the fattest and least forgiving — every failure there is a container failure rather than a platform lesson. Mitigation: the worker image is pre-built and pre-imported into k3s during provisioning, so the challenge is configuration and deployment, not docker build.

Supporting services

One service, one IdP, no mail

Terraform state service

An HTTP backend — GET, POST, DELETE, basic auth, volume-backed. Partitioned by path as /state/<participant>/<logical>/<env>, with a per-student bearer token minted at sandbox setup and injected as TF_HTTP_PASSWORD. Remote state also means a student who restarts their sandbox keeps their work.

The local file backend is retained as a working implementation, selected by stateBackend: local. Not for production — because it is the only thing a student can debug when the Fly service is unreachable, and egress failure is the portal’s documented number-one sandbox complaint.

A single Fly machine makes “apply succeeded, state write failed” more likely than the demo’s original S3 design did. That is exactly why AttemptImport ports over rather than being dropped: it re-adopts orphaned resources instead of duplicating them.

Identity via SAML

No mail anywhere in this design. Students authenticate against an Okta developer tenant configured as the account’s SAML IdP. Temporal still sends an invitation email when the user is created; nobody ever reads it. That also dissolves the constraint which motivated a relay in the first place — one address maps to one Temporal Cloud account permanently, so a platform engineer whose work address already sits in another account is un-invitable. Under SAML the address is a workshop-owned identifier, not their real mailbox.

  • 15 fixed identities, student-NN@domain, bound to the slot pool. Slot 7 owns ws-7-staging, ws-7-prod and student-07@domain — one lease derives everything, and identities are reused across cohorts rather than recreated.
  • Provisioned with temporalcloud_user in Terraform. Pleasingly on-thesis: the workshop’s own attendee identities are provisioned as code.
  • Okta is the kill switch. The reaper deactivates the Okta user — instant, and no Cloud API call. Cloud user records persist between cohorts.
  • SCIM is not needed. Fifteen fixed identities provisioned once need no lifecycle sync, and it is Enterprise-tier or a $500/month Business add-on.
  • Ask support to disable social logins, so there is exactly one login path and nobody lands on “Continue with Google”.
  • Okta developer edition over Entra ID, which gates SAML for custom apps behind a paid tier, and over Google Workspace, whose Temporal setup instructions are still being written.

The domain is needed only as an identifier namespace and for the IdP-domain mapping support asks for. No MX, no SPF, no DKIM, no mailbox.

This design is contingent on one unverified claim. Temporal support has stated that JIT account creation is not supported, so users must be created before they can sign in — fine, the control plane creates them. What is not yet confirmed is whether a created-but-never-accepted user can complete a SAML login without opening the invitation email. Ask before building; if acceptance is required, the mail relay returns.

Sandbox

Prebuild aggressively

n1-standard-4, 16 GB, k3s. The portal’s build already needs this for uv, Docker and code-server; this one drops Prometheus and Grafana but adds a Go toolchain, k3s and Vault.

  • Go toolchain; uv sync complete
  • terraform plus a warm provider plugin cache — a cold terraform init against temporalio/temporalcloud is a silent two-minute stall on challenge 1
  • Vault binary; k3s installed but not started
  • The managed worker image built and imported into k3s’s image store

k3s over k3d: the Kubernetes-auth switch in challenge 4 is more honest against a real kubelet, and nothing is torn down repeatedly. Measure the boot rather than guessing — the portal’s loading messages exist because that build is already slow.

Numbers

Quotas, names and reaping

ItemValueNote
Students15Self-paced, so arrivals overlap unpredictably
Namespaces per student2staging + prod, one region
Namespace quota to request40Default is 10; headroom for overlap and your own testing
Cloud metrics budget180 / hrPer account. Largely moot — metrics endpoints are out of scope
Okta developer tenant1Free. 15 fixed identities, reused across cohorts

Name recycling. Temporal Cloud reserves namespace names after deletion, so names must not derive from participant ids — a naive scheme burns names permanently. Physical names are ws-<slot>-<env>, where slot is a small integer leased from a pool workflow. Slot 7 is reused by design, so reserved-after-deletion stops mattering.

Reaping. A reaper workflow — not a script — keyed to the participant id, holding a TTL, accepting the same extendMs and revoke signals the portal’s invitation workflow already has. Abandoned sandboxes must return their slots to the pool.

Risks

What is still likely to bite

  • Challenge 4 remains the fattest slot even with the image pre-built. Watch it in the first dry run; the fallback is splitting it across 4 and 5, which costs the stopwatch.
  • Students hold Global Admin. The same blast radius the portal already accepts, mitigated by slot names and the reaper. A griefing student can delete another’s namespaces.
  • Single-machine state service. Mitigated by AttemptImport, but a Fly deploy mid-workshop will fail somebody’s apply.
  • Sandbox boot time is unmeasured and the prebuild list is long.
  • One unverified assumption gates the whole identity design. Whether a pre-created, never-accepted user can complete a SAML login without opening the invitation email is unconfirmed. Ask first — if the answer is no, the mail relay returns and Google Workspace rejoins the critical path.
  • Okta becomes the access control plane. Between cohorts, 15 standing Global Admin users sit in the account gated only by Okta. A misconfigured tenant is a live-credential problem, not an inconvenience.
